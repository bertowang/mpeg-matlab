0读前须知：这个工程在做什么

阅读本章后，你应能说清「本工程的输出到底是什么」。

本工程用 MATLAB 演示经典 MPEG-1/2 式混合编码的原理链路：读一段 AVI，按 10 帧一组的 GOP 处理，对每帧做预测、变换、量化，再本地解码重建，最后把重建帧写成新的 AVI。它让你看见每一步的中间结果，而不是得到一个可播放的压缩文件。

最容易产生的误解 看到 decoder.m 里的 MPEG 标准 Huffman 表，就以为这是一套完整编解码器。实际上这些表只被当作参数层层传递、从未被解析；ZigZag.m、dezigzag.m、chkcategory.m、makeLayers.m 全库没有调用点。第 9 章会专门讲这个「空座位」。
配套文档 工程说明、文件清单、运行方法与已知代码债见同目录 README.md；本教程只讲原理与阅读顺序。

1先修：视频为什么能压缩

阅读本章后，你应能用「冗余」二字解释 I/P/B 帧存在的理由。

两种冗余

把视频想成一本翻页动画书：相邻两页通常只挪动了一点点，而单页内部大片区域颜色相近。于是有两类可去掉的重复信息：

  • 时间冗余：第 n 帧和第 n−1 帧很像 → 不必重传整帧，只传「哪一块从哪儿搬来」和「搬来之后还差多少」。
  • 空间冗余：一帧内相邻像素值接近 → 变换到频域后，能量集中在少数低频系数上，高频系数可以大胆丢掉。

于是有了三种帧

帧类型参考谁压缩率在本工程中的实现
I 帧（Intra）只靠自己最低forwardDCT 直接对整帧做 DCT 量化
P 帧（Predicted）前面的已重建帧中等compensatedFrame.m：先运动补偿，再编码残差
B 帧（Bi-directional）前、后参考帧最高bFrameProc.m：本实现是择一单向参考
为什么 I 帧不能省 如果所有帧都靠前一帧预测，误差会一直传递下去，而且没法从视频中间开始播放。每隔若干帧放一个 I 帧，等于定期「重新对表」；这一组帧就叫 GOP（Group of Pictures）。

一个必须记住的数字

本工程把帧统一缩放到 128×128，宏块边长 mbSize=8，所以一帧被切成 16×16 = 256 个块。这正是 main44.m:9 里 motionVect = zeros(2,256) 的由来：每个块存一个二维运动矢量。后面所有循环都按「步长 8」扫描这 256 个块。

2全局鸟瞰：一条流水线

阅读本章后，你应能对着图说出每个主要函数的调用顺序。

main44.m 是唯一的入口脚本。它先处理第 1 帧（I 帧），然后进入 for i=1:10:60 循环，每个循环体处理一个 10 帧 GOP；循环末尾把该 GOP 的最后一帧设为下一组的起始 I 帧。

1
准备：main44.m:7-30 创建输出 AVI、读入 Qtable2.txt 量化表、设置 mbSize=8 / p=7、声明 10 个 global 变量。
2
首个 I 帧：main44.m:30-42 读第 1 帧 → forwardDCT → inverseDCT 得到本地重建 bufferI1 → decoder(…，1，…)。
3
循环 6 个 GOP：main44.m:44-222 每个 GOP 由 GOP(j) 取 9 帧，按 P4 → B2/B3 → P7 → B5/B6 → I10 → B8/B9 的编码顺序处理。
4
显示与写盘：main44.m:141-225 把 10 个 global *d 逐帧 imshow + getframe 写入 2.avi。
注意「编码顺序 ≠ 显示顺序」 要先有后面的 P 帧才能编它前面的 B 帧，所以代码里先算 P4、再算 B2/B3，最后才按显示顺序 1…10 播放。第 3 章会把这条时间线画开。

3GOP 与三种帧的排布

阅读本章后，你应能解释为什么 B 帧必须「先编后播」。

本工程固定使用 10 帧 GOP，结构写在 main44.m:20 的注释里：IBBPBBPBBI。GOP.m 一次从 AVI 读出 9 帧（i+1 … i+9），加上上一组留下的第 1 帧，凑成 10 帧。

GOP 之间怎么接上

循环末尾 main44.m:220-222 执行 I1=I10; bufferI1=bufferI10; I1d=I10d：把本组最后一帧（编号 10）当作下一组的第 1 帧。这也是为什么循环写成 for i=1:10:60，而 GOP(j) 里用 j = i - round(i/10) 做帧号偏移。

一个小练习 数一数：main44.m:44 的循环跑 6 次，每次读 i+1 … i+9，最大读到第几帧？答案是 55（不是 60）。读入的 noframe = aviinfo('news.avi').NumFrames 实际上完全没被用到。这类「写了但没用」的变量，在这个教学工程里不少，读到时不必困惑。

4I 帧：DCT、量化与 ZigZag

阅读本章后，你应能解释「为什么量化后会出现大量零」。

I 帧不参考任何别的帧，只能压缩自己。做法是把图像切成 8×8 小块，逐块变换到频域，再把不重要的高频系数抹掉。

对应到代码

forwardDCT.m 只有 5 行有效代码：

Im = Im - 128;                              % 把 0..255 平移到以 0 为中心
T  = dctmtx(8);                            % 8×8 DCT 变换矩阵
y  = blkproc(Im,[8 8],'P1*x*P2',T,T');    % 逐块做 T·x·T'
JQ = blkproc(y,[8 8],'round(x ./ P1)',array);  % 逐元素除以量化表并取整

inverseDCT.m 是对称的：先 .*array 反量化，再 T'·x·T 反变换，最后 +128 平移回来。量化是有损的、不可逆的一步：除完取整，小数部分永远丢了，所以解码图不可能和原图完全相同。

用具体数字建立直觉 量化表左上角是 16，右下角是 131（见 Qtable2.txt）。假设某个高频 DCT 系数是 40，除以 131 再取整得 0；解码时 0×131 还是 0，这个细节就永久消失了。而左上角的 DC 系数除以 16，保留得相对完整。这就是「保留轮廓、丢掉纹理」的量化策略。
B 帧用 0.5*array（量化步长减半），因此 B 帧残差保留得更精细——因为 B 帧要被压得更狠，作者用更细的量化来补偿质量。
为什么是 128 像素值原本是 0…255（无符号），DCT 希望输入围绕 0 波动。减 128 后，大片均匀区域接近 0，变换后非零系数更少。解码端 +128 再还原。第 7 章会看到 B 帧分支多减了一次 128，那是一个特殊 hack。

5运动估计：在参考帧里找那一块

阅读本章后，你应能说清 MV 是什么、MAD 是什么、TSS 为什么快。

运动估计要回答一个问题：当前帧的这个 8×8 块，是从参考帧的哪个位置搬过来的？答案是一个二维位移 (dy, dx)，即运动矢量 MV。

全搜索太慢，于是有了快速算法

半径 p=7 时，全搜索（ES）要比较 (2×7+1)² = 225 个候选位置 × 256 个块 × 64 个像素。三步搜索（TSS）用「由粗到细」的 3×3 点阵，只需约 25 个候选点：

工程里其实放了四族算法

算法文件（P 帧 / B 帧）思路是否接入主流程
ES 全搜索motionEstES.m / BmotionEstES.m穷举搜索窗内每一点，最准最慢否
TSS 三步搜索motionEstTSS.m / BmotionEstTSS.m3×3 点阵、步长减半是（compensatedFrame.m:3、bFrameProc.m:4,7）
DS 菱形搜索motionEstDS.m / BmotionEstDS.m大/小菱形模板交替否
ARPS 自适应十字motionEstARPS.m / BmotionEstARPS.m用相邻块 MV 预测搜索起点否
最好的入门实验 把 compensatedFrame.m:3 的 motionEstTSS 换成 motionEstES，对比 2.avi 的清晰度和运行时间。你会直观看到「搜索策略 → 预测质量 → 残差大小 → 重建质量」的因果链。这就是这个教学工程最有价值的用法。

6运动补偿与残差：只编码「差多少」

阅读本章后，你应能画出 P 帧编码的加减法关系。

有了 MV，就可以从参考帧把对应块搬过来拼成预测图 imgComp（motionComp.m），再用当前帧减去预测图得到残差。残差大部分接近 0，交给 DCT/量化后系数更稀疏，这就是压缩的来源。

motionVect  = motionEstTSS(Im, bufferImage, mbSize, p);   % ① 找 MV
imgComp     = motionComp(bufferImage, motionVect, mbSize); % ② 拼预测图
imageSubtract = double(imsubtract(uint8(Im), uint8(imgComp))); % ③ 相减
streamP     = forwardDCT(imageSubtract, array);            % ④ 变换量化
JQ2         = inverseDCT(streamP, array);                  % ⑤ 本地解码
bufferImageP = double(imadd(JQ2, imgComp));                % ⑥ 重建参考帧
容易看漏的一步 第 ⑤⑥ 步看起来「多此一举」：既然刚编码完，为什么立刻又解码一遍？因为解码端拿不到原始帧，它只能看到经过量化损失的重建图。编码器必须用同一张失真的图当参考，才能保证两边预测一致。详见第 8 章。
P 帧与 B 帧的数值差异 P 帧残差没有减 128（compensatedFrame.m:5），而 B 帧在 compensatedFrameB.m:6-7 里额外 imsubtract(…,128)，解码端 bdecoder.m:6 再 +128 补回。这是原始教学代码留下的不对称 hack，不是标准规定，阅读时按「作者为了配合 imsubtract 的 uint8 截断做的数值平移」理解即可。

7B 帧：借前一帧，还是借后一帧

阅读本章后，你应能说清 flag 变量的含义。

标准 MPEG 的 B 帧可以取前、后参考的平均。本工程做了简化：分别做两次运动估计，然后挑一个参考帧，用 flag 告诉解码器挑的是哪一个。

[motionVect1, zeroMatrixCount1] = BmotionEstTSS(B, I, mbSize, p);
[motionVect2, zeroMatrixCount2] = BmotionEstTSS(B, P, mbSize, p);
if zeroMatrixCount1 <= zeroMatrixCount2
    flag = 0;  B = bFrameCal(B, I, ...);   % 用前参考
else
    flag = 1;  B = bFrameCal(B, P, ...);   % 用后参考
end

flag 随后被传进 decoder.m：identifier 决定帧类型（1=I1、2=B2、3=B3、4=P4 … 10=I10），flag 决定 B 帧取哪个参考（见 decoder.m:195-204）。这两个「魔法数」就是本工程解码器的全部调度信息。

与标准的差别 标准 B 帧通常做双向平均（前、后各取一块再加权），而这里只取一侧。另外「零 MV 个数」只是启发式判据，没有计算码率与失真的权衡——真正的 RDO 会在相邻工程 videoCodecDemo 里出现，用 J = D + λR 做决策。这正是两个工程知识代际的分水岭。

8解码器，以及初学者最容易困惑的「误差漂移」

阅读本章后，你应能回答：编码器里为什么藏着一个解码器？

解码器做了什么

decoder.m 用一个 if identifier==… 链做分派，三个薄封装 Idecoder / pDecoder / bDecoder 最终都走到 deRunLength.m → inverseDCT.m；P/B 帧再加回运动补偿图。结果不通过返回值传出，而是写进 10 个 global 变量（I1d、P4d、B2d …），由 main44.m 读取显示。

用一句话回答

因为量化是有损的，解码端只能看到「重建后的、有点糊的」帧。如果编码器拿原始清晰帧去做运动估计，而解码器拿糊帧去补偿，两者的预测图就会不一致，误差一帧帧叠加，画面越往后越坏（drift，误差漂移）。所以编码器必须自己先走一遍解码流程，用和解码端完全相同的重建帧当参考。

本工程的两处实现细节 ① 编码端的重建是 compensatedFrame.m 里的 bufferImageP；② 解码端的重建是 decoder.m 里的 global *d。它们走了两条略有差异的代码路径（尤其 B 帧的 ±128 处理），这也是阅读代码时容易对不上的地方。
PSNR 在哪 imgPSNR.m 已经写好但没有接进主流程。想定量评估重建质量，可以在 main44.m 显示每帧时调用它，比较原始帧 I1 与重建帧 I1d。这也是一个很好的课后练习。

9熵编码的空座位

阅读本章后，你应能指出本工程缺了哪两块，以及它们为什么重要。

一条完整编码链路的最后两环是：把量化系数变成一串紧凑的比特（ZigZag + 游程 + 变长码）和把比特写成码流。本工程把位置留出来了，但没有坐满。

留白的文件原本应该做什么实际状态
ZigZag.m / dezigzag.m把 8×8 系数按之字形排成一维，让零集中在末尾实现了索引表，但无调用点
chkcategory.m按 VLC 的 category 解析系数幅值实现了，但无调用点（且用了旧版 bitcmp 语法）
makeLayers.m / deRunLength.m分层 / 反游程解码前者是恒等函数 c=c，后者只转调 inverseDCT
decoder.m:6-162 的 MatAC / MatDCMPEG 标准 AC/DC 系数 Huffman 表定义在，向下层层传参，从未被查表
为什么留白反而是好事 对初学者来说，一个「只到量化系数为止」的工程恰好把最核心、最可视化的部分单独拎了出来，不会被位流语法淹没。补全它，就是一份完整的课程设计：
① 对 JQ 做 ZigZag 扫描；② 统计 (run, level) 游程对；③ 用 MatAC/MatDC 查表写成比特；④ 写一个 .bit 文件；⑤ 解码端反向还原并计算 PSNR；⑥ 换成 ES 搜索、调整量化表，画出「码率—PSNR」曲线。

自测题（点击展开答案）

1. 一帧 128×128、mbSize=8，为什么 motionVect 是 2×256？

128/8 = 16，每方向 16 个块，共 16×16 = 256 个宏块；每个块需要一个二维 MV（dy、dx），所以是 2 行 256 列。见 main44.m:9 与 motionEstTSS.m:20。

2. 量化表右下角的数值为什么比左上角大？

右下对应高频细节，人眼不敏感，除以更大的数后取整直接变 0，从而省下大量系数；左上低频（含 DC）决定整体亮度与轮廓，需要精细保留。见第 4 章与 Qtable2.txt。

3. 为什么编码 P4 之前，代码已经有一张 bufferI1？

因为 I1 编码后立刻本地解码了一次，得到与解码端一致的重建帧。P 帧的运动估计必须对着这张重建帧做，而不是对着原始 I1 做，否则会误差漂移。见第 8 章。

4. 为什么代码先算 P4 再算 B2、B3？

B 帧要用「后面的」P4 作参考，必须等 P4 的重建帧就绪才能编码；但播放仍按显示顺序 1…10。这是编码顺序与显示顺序的分离。见第 3 章。

5. 本工程算不算「生成了压缩视频文件」？为什么？

不算。2.avi 是重建帧序列（无压缩 AVI），不是压缩码流；量化系数 JQ 只存在于内存，Huffman 表从未被查用，没有写出任何比特流。见第 0、9 章。

6. 把量化表整体乘 2，画面和系数会怎么变？

除数变大 → 更多系数被量化成 0 → 反量化后细节丢失更多，重建图更模糊，PSNR 下降；但系数更稀疏，若接上熵编码会得到更短的码流。这正是「质量—码率」权衡的雏形。

7. 本工程的 B 帧与标准 MPEG 的 B 帧有什么不同？

标准常用前、后参考的双向加权平均；本工程用「零 MV 个数」启发式择一参考（flag=0/1），不做双向插值，也不做率失真判决。见第 7 章。

11动手运行与常见报错

阅读本章后，你应能独立把 demo 跑起来，并知道报错时先查哪里。

cd('…/mpeg-matlab')   % 必须：所有数据文件都是相对路径
main44                % 脚本开头 clear all 会清空当前工作区

预期现象：弹出图像窗口逐帧显示重建帧，命令行打印 GOP 编号与耗时 toc，结束时当前目录多出 2.avi。

现象原因处理
未定义函数 aviread / avifileMATLAB 新版已移除旧 AVI API改用 VideoReader / VideoWriter，或装旧版 MATLAB（约 R2010b 之前）
未定义函数 dctmtx / blkproc / imresize缺少 Image Processing Toolbox安装该工具箱；blkproc 新版需换 blockproc
找不到 news.avi 或 Qtable2.txt当前工作目录不是本工程根目录cd 到本目录（代码里没有 addpath，光加路径不够）
Linux 下提示找不到 pDecoder / bDecoder文件名 pdecoder.m 与内部声明名大小写不一致统一大小写；Windows 因文件系统不区分大小写才「侥幸」能跑
矩阵下标越界改了帧尺寸却没同步 motionVect=zeros(2,256) 与 inverseDCT 里写死的 1:8:256帧尺寸保持 128×128，或把写死的 256 / 8 全部参数化
运行后工作区变量全没了main44.m:2 的 clear all在独立会话中运行，或注释掉该行
推荐的三组对比实验 ① 固定量化表，把 TSS 换成 ES，比较画质与耗时；② 固定搜索算法，把量化表整体乘 2 / 除以 2，用 imgPSNR 定量对比；③ 修改 for i=1:10:60 处理更多 GOP，观察 GOP 衔接处的重建质量。每做完一组，回看第 6、8 章的图，把现象与链路对应起来。

残差怎么编8×8 DCT + 固定量化表Matching Pursuits 稀疏原子字典，不用 DCT
熵编码Huffman 表在，未接线；无码流Range Coding，输出真实 .enc 码流
决策方式零 MV 启发式、固定 QPJ = D + λR 率失真判决 + λ 码控
运动估计整像素、固定 8×8 块、四族快速搜索整/半/四分之一像素、可变块划分、OBMC
输入输出AVI 进、AVI 出YUV 4:2:0 单帧进、.enc + RD 曲线出

因此不合并。两者不是同一系统的上下游模块，而是同一知识领域的两个平行实现：数据格式、码流、残差表示、运动估计接口完全异构，无法互相调用；强行拼在一起既不能补全本工程的熵编码，也不能给对方提供 DCT 模块。此外对方工程中的 @uint32 / @uint8 类方法重载会改变整个 MATLAB 会话的整数运算语义，与本工程的 uint8 图像运算同跑会产生静默错误。

推荐的学习顺序 先通过本工程把「预测 → 残差 → 变换 → 量化 → 闭环重建」这条主干彻底弄懂（第 1～8 章），再去看 ../videoCodecDemo/tutorial.html，重点体会三个升级：从固定块到可变块、从启发式到 RDO、从系数矩阵到真实码流。这样过渡最省力。
